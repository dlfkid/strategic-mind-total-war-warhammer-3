# 后续路线图

以证据推进阶段，不先承诺发布日期。项目边界见 [设计原则](design-principles.md)，判定标准见 [MVP](mvp-boris.md)。

## 阶段 0：调查与仓库初始化

本次交付：README、开发约定、原则、第一轮可行性、来源快照、本地环境、API 登记、MVP 与兼容性测试规划。已有 Git/GitHub 仓库继续使用，保留原始许可证。只完成离线文档初始化，不把任何游戏 API 标为通过。

## 阶段 1：接入实际游戏与最小观察包

先完成 E0、E1：取得当前版本数据与测试档，验证加载、日志、重大事件、有限记忆、保存恢复、可见性和一条原版消息。按需加入最小源码和纯逻辑测试，单次包只验证一个问题。

进入条件：可运行的游戏环境和实际数据。退出条件：API-01–07 有可复核记录；无法观察与恢复状态则先修正环境或缩减方案。

## 阶段 2：鲍里斯战略闭环

完成 E2，必要时独立完成 E3，再完成 E4。核对原版鲍里斯机制，展示记忆确实参与决策，并记录干预、实际结果与玩家获知之间的关系。用多个前置局面建立对照，检查归还、存档和性能。

退出时选择有证据支持的产品定位：倾向调节、有限脚本导演、观察纪事，或继续局部战略引擎。达到止损条件时不直接增加更多派系或更复杂评分。

## 阶段 3：有限扩展 Campaign AI

只在阶段 2 通过后加入第二个具有不同战略目的的领主，验证架构能表达差异。此时再增加关系记忆、较长计划和更多外交案例；每项都有真实事件输入、干预出口、观测和性能预算。多军团协调独立研究，不视为单军团控制的自然延伸。

## 阶段 4：独立 Victory Conditions

选一个有可靠状态输入的派系使命，先做进度追踪，再验证正式胜利。成就作为单独兼容性调查。独立安装、不依赖 Campaign AI、与原版任务共存通过后，再扩展妙影、诺斯卡、海盗、鼠人和帝国等不同目标类型。

## 阶段 5：独立 Battle AI 探路

先验证普通战役战斗的非侵入加载和单单位控制归还，再选一个远程目标/防骗箭实验。野战、攻城、任务战斗和联机分开验收。若普遍接入或控制权恢复不可靠，保持限定场景，不承诺改造完整内部战斗 AI。

## 下一次开发的具体起点

提供或定位实际测试机上的游戏路径与一份米登领相关存档，记录安装清单，从当前包内核对加载入口、鲍里斯身份、地区 key、消息类型及最小相关 API。随后只实现 E0 的加载/日志探针。此时再根据实际环境选择打包与测试工具；不需要为了文档阶段建立新工作区、安装全套依赖或创建新的 GitHub 仓库。
