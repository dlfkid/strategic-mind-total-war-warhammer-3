# 兼容性与测试规划

状态：计划；当前没有游戏测试结果。实机记录使用 [API 模板](research/api-register.md)，按 [MVP](mvp-boris.md) 顺序执行。

## 三层验证

| 层 | 要验证的事情 | 不代表什么 |
| --- | --- | --- |
| 离线纯逻辑 | 相同输入可重放；约束优先；记忆改变决策；衰减/上限；计划取消；事件去重；披露删减 | 不代表游戏 API 或 AI 调度工作正常 |
| 包与静态检查 | 唯一 key、脚本路径、Lua 兼容语法、DB 引用、本地化、只包含预期差异 | 不代表引擎实际执行行为 |
| 实机 | 事件、读回、行动与归还、可见性、消息、存档、性能和共存 | 单次通过不代表所有局面/平台/Mod 组合兼容 |

当前已有文档、交接检查工具与相应测试，按 [开发工作流](development-workflow.md) 检查。它们不验证游戏功能；Mod 代码出现后增加相应纯逻辑测试。打包工具与 Lua 解释器须先记录版本，不提前安装一套与实际测试机不符的环境。

## 必测矩阵

- 新局、原版旧档首次启用、已有 Mod 存档重载，以及版本升级后缺键/未知 schema 的保守处理。
- 保存发生在意图形成、命令提交、行动进行、归还控制、消息披露各阶段时，读档不会重复行动或重复通知。
- 非人类对象变为人类、合邦、派系灭亡、将领负伤/死亡、CQI 失效与重建、无领土派系、海上位置。
- 已探索但无视野、可见、伏击/隐藏、视野消失；消息中的历史事实与位置逐项检查，而非只检查一个角色。
- 通知关闭后仍正常记录事实；重开通知不无界补发；事件队列和记忆达到容量上限后仍能追溯已披露原因摘要。
- 不可达、行动点不足、非预期回合、目标失效、API 缺失或正常返回但未生效；每次失败有界退出。
- 单独安装三个组件；Campaign AI 与原版鲍里斯机制；随后分别与一个 AI Mod、一个胜利条件 Mod、消息/UI Mod 共存。
- 联机作为独立阶段：同步状态、确定性、玩家视野隔离、掉线/重连。未通过前标为未支持/未验证，不以单机结果承诺。

## 控制恢复与移除

关闭功能不等于卸载包。被接管角色必须在明确退出、失败、超时和读档恢复时归还；记录本 Mod 持有的对象与状态，重载时重新取得接口。不得把其他 Mod 的控制状态或态度修改当成自己的。

没有经验证的身份隔离清理接口时，不在共存环境使用派系对级别的 `clear_all_*` 清理。优先限时状态，记录该限制，必要时只在无其他 Mod 的测试档中验证。

卸载前须有已经测试的“关闭干预并归还控制”步骤。包已经移除后，本 Mod 无法再运行清理逻辑，因此不能承诺任意时点删除都安全。不能用“纯脚本”自动推断旧档兼容或可卸载。

## 性能与容量

同一台机器、同一预置存档、相同画面/日志设置分别测原版、观察模式和干预模式。记录完整 AI 回合耗时与 Mod 评估耗时；各做至少 5 个回合，报告中位数和最大值，并注明样本小、随机行为与缓存等干扰。

第一轮暂定门槛：Mod 额外回合耗时中位数不超过基线的 5%，且无超过 1 秒的反复附加停顿；两项都满足才扩展。基线太短或波动超过差异时报告 `INCONCLUSIVE` 并补样，不强行判断。该门槛是工程目标，不是测量结果。

先限定事件与派系，避免每帧扫描全地图。分别记录事件数、历史条目数、活动意图、队列长度、日志行数和存档大小变化。长时检查计划至少运行 50 回合或用离线容量测试配合较短实机观测；离线通过不能替代长期游戏稳定性。

## 游戏更新后的回归

记录旧/新版本、Build ID、平台、相关原版脚本与 DB 导出哈希、工具/schema 版本。先对比入口、签名、表字段、key 和原版机制，再复跑最小加载、日志、事件、存档、可见性、一次干预及归还、一次消息。

更新后默认只沿用仍有证据的能力。不能单靠 `type(function) == "function"` 判断兼容；接口可能存在但静默失效。受影响功能降级并记录一次诊断，避免重复刷屏。必要时暂停该项干预，保留可运行的只读部分。

当前公开版本 9.0.3 仍修复任务保存/读取和胜利目标（[官方公告](https://community.creative-assembly.com/total-war/total-war-warhammer/forums/7-patch-notes-amp-announcements/threads/16126-total-war-warhammer-iii-patch-9-0-3)），因此 Victory Conditions 的进度恢复与版本切换应单独验收。

## 正式胜利和成就

额外使命完成、正式战役胜利、胜利 UI 与 Steam 成就是四项验收。检查当前原版胜利脚本、胜利类型和成就条件后，使用用户同意的测试账号/存档进行可能写入平台状态的成就测试；本阶段不主动授予或重置成就。

多种胜利 Mod 共存时，先定义哪方拥有正式胜利注册与进度；没有协调方案就声明冲突。不要先取消原版胜利再测试新胜利能否触发。

## 发布与证据

每个发布候选记录 Git 提交、包哈希、游戏版本/Build ID、平台、已测 Mod 组合、未测部分和已知问题。发布包只含所需源码、DB 差异与本地化，不夹带原版数据和个人诊断。没有 Windows 实机结果不能从 macOS 的文档检查推断 Windows 兼容，反之亦然。
