# 项目目标与设计原则

基于用户提供的《Codex Work 项目启动 Prompt V2》整理。日期：2026-10-14。本文是项目方向与本阶段工作边界，不代表尚未实测功能已经可用。

## 成功标准

玩家经历一场战争后，能够理解对方发动战争的原因、采用战略的理由，以及自己的行为如何改变了世界。判断依据是可解释的决策、真实后果与符合背景的差异，而非 AI 胜率或攻击次数增加。

本阶段交付调查、证据记录、精简仓库、兼容性测试规划和可实机验证的 MVP 计划。不开发完整引擎，不覆盖全部派系，不制作发行包。

## 三个独立组件

Campaign AI 最高优先：先做局部威胁识别、持续意图、受限执行、历史记忆与纪事。Victory Conditions 独立跟踪使命与完成条件，不能要求 Campaign AI 才能工作。Battle AI 后置并独立验证；战役侧接口存在不能说明战斗侧具有同等能力。

首版 Memory 和 Chronicle 只供 Campaign AI 使用。未来若 Victory Conditions 需要同类工具，可以在构建时复用少量纯逻辑；每个包仍使用独立命名空间和存档键，避免共享运行时互相覆盖。不提前引入公共框架。

## 三层决策

| 层 | 职责 | 约束 |
| --- | --- | --- |
| Common Sense | 合法目标、行动可达性、兵力与补给风险、核心领土安全 | 硬约束独立于风险偏好，性格不能允许无效接口或非法目标 |
| Faction Doctrine | 种族文化、外交认知、军事传统和共同利益 | 战略倾向可以被局势推翻，不能写成永久阵营禁令 |
| Lord Personality | 使命、宿敌、野心、风险承受能力 | 作用于同一个状态和评分过程，不能绕过观测与证据规则 |

优先使用确定性、可解释、性能可控的规则与效用评分。运行时不要求大语言模型或外部服务。计划应有开始理由、有效期、继续条件、退出条件和冷却，防止每回合改换目标。

## Memory 必须改变决策

只保存重大事件，至少包含参与者、地点、发生回合、事件类别与证据来源。关系记忆有累积、上限和衰减；保留原因引用。通过“有记忆 / 无记忆”的同输入重放验证其确实改变目标或优先级，不能只改变文字。

内存、存档与日志均设置预算。已有存档缺少数据时从空历史开始，绝不补写未曾记录的往事。实体消失、受伤、合邦或更换将领后，旧 CQI 必须重新校验。存档兼容、升级、降级和移除分别测试。

## 决策、执行与故事

系统保留两条输出：面向开发者的完整诊断，以及面向玩家、按可见性删减的叙事。推荐的内部证据链为：

```text
真实事件 → 记忆 → 三层判断 → 战略意图 → 执行请求
                                         ↓
                              结果观测 → 玩家获知 → 纪事
```

每条箭头需要稳定 ID 或明确记录支撑。仅观察到一支军队向敌人移动，不能补写“它因某场历史战争而出征”。倾向干预后发生的行为，若因果无法确认，开发日志应保留不确定性，玩家文本只陈述足以支持的事实。

事件发生与玩家获知分开：内部可以在第 38 回合生成意图，第 42 回合才展示已观察的行动。军队当前可见不表示它的隐藏目标、另一支不可见军队和秘密盟约可披露。事件、相关地点与叙事中每一项事实都要检查可知性；缺少可靠检查就延迟或省略。

无证据时不能把贸易协定写成商队侵犯森林。如果未来采用“边境压力”等抽象机制，先定义可计算的输入、状态与后果，并在文本中保持抽象，不能伪装成真实单位事件。

## 纪事体验

优先原版消息和历史记录，展示重要战争目标、外交变化、宿敌事件及玩家行为的重大后果。预设去重、冷却、数量上限和关闭通知选项；历史筛选与自定义 UI 后置。原版历史记录可否充分满足浏览需求仍待实测。

面向玩家的叙事使用战锤背景语言。它只能呈现有依据且获准披露的部分，不能显示内部权重、失败调用或开发者秘密信息。

## 稳定性与兼容性

优先公开或已验证的 Mod 接口，游戏适配和纯逻辑分开。避免内存修改、startpos、整表覆盖及大型原版脚本替换；不通过无限资源、隐藏增益或生成军队提高难度。

能力缺失时只关闭相应干预，并输出原因。不能因为函数没有抛错就继续重复调用。单个对象接管必须有时间预算和归还机制，不能将安全回退变成全派系永久锁定。

更新后的兼容性由指定版本的回归测试定义，不能承诺未来永不失效。项目扩展以 MVP 的实机证据为条件，止损标准见 [MVP 计划](mvp-boris.md)。
